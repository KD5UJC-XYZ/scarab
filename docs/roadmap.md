# Roadmap

What remains after the v0.1.0 research preview. Item IDs (A1, B3, ...) are stable: issues and pull
requests reference them, and they are not renumbered when items are done (done items are marked, not
deleted). Priorities:

- **P0** is needed for the research preview or blocks collaborators.
- **P1** is needed for a full reference-compatible node.
- **P2** is hardening or nice-to-have.

Each open item links to its GitHub issue, which carries its state (`status:` labels) and milestone; how items move from idea to done is in [process.md](process.md). Large items have a [design document](design/README.md), and the decisions behind them are [ADRs](adr/README.md). How each area stands today is in [compatibility.md](compatibility.md).

- **B26** (P1, done; one part open) The boundary that enters Allegra returns the outputs to Byron redeem (AVVM) addresses to the reserves (`returnRedeemAddrsToReserves`, run by the Shelley to Allegra translation before the boundary's tick); the node's boundary did not, so its reserves from epoch 236 were 318,200,635 ada below the reference's and every reward calculated from then on was short (mainnet block at slot 17,020,941, transaction 48f567e5 withdrawing the leader reward 351,635,274 of pool ffdf1b8f for epoch 235, where the node had 351,050,635; `MainnetAllegraReservesSuite` reproduces both amounts from the real inputs, `AllegraRedeemStoreSuite`). - **B27** (P1, done) A snapshot of a mainnet state in Shelley was refused by the ledger-state mirror (`NetworkMismatch(expected = 1, actual = 0)`): the pool ff5181ba, registered at protocol version 2 with a reward account on network 0 (B22), stays registered past epoch 237, and no snapshot was written from the Byron to Shelley handover on, so every restart of a mainnet follower replayed from the last Byron snapshot. No format change (`MainnetPoolNetworkSnapshotSuite` on the real registration, `PoolNetworkQuerySuite`, the mirror laws over accounts on either network; [findings.md](findings.md)). Open: the node's own state still holds the registration's network for a registered pool (nothing reads it but the mirror and the two queries, which normalise it); storing it as the reference does, at registration and adoption, is a later cleanup.
- **B28** (P1, done) Before Babbage an address in a transaction output may be followed by bytes that belong to no address, and the ledger drops them: the decoder of a Shelley to Alonzo era does not check that the address used every byte (`fromCborBackwardsBothAddr`, cardano-ledger-core 1.21.0.0), the one of Babbage and Conway does. Mainnet block at slot 39,249,764 (epoch 288, Mary), transaction 369826b2: output 0 is a base address of 57 bytes with 21 bytes after it, and the node refused the block with `base address length` (`MainnetGarbageAddressSuite`, `MainnetGarbageAddressStoreSuite`). `Address.Mode` (`Backwards` below Babbage, `Rigorous` from it, by `Address.Mode.of(era)`) is threaded from `Tx.fromBlock` through `TxBody.decode` and `TxOut.decode`; the address in the set is the cropped one, as in the reference, the output keeps its own bytes, the transaction id is over the body as it came ([findings.md](findings.md)). The pointer normalisation of the same decoder is B29.
- **B29** (P1, done) A pointer address in an output is read as the reference reads it: the decoder of a protocol version below 9 normalises a pointer whose slot does not fit a Word32, or whose transaction or certificate index does not fit a Word16, to `Ptr 0 0 0` (`mkPtrNormalized`, `Credential.hs:270-285`, through `decodePtrLenient`, `Address.hs:780-788`; the natural is a Word64 that wraps) and keeps the address written again (`cAddrNormalized`, `Address.hs:470-476`, `putPtr`), and from version 9 (Conway) it refuses the address (`decodePtr`, `Address.hs:769-777`, the naturals read with at most 5 and 3 groups). The node kept the exact pointer, which the Haskell ledger state cannot hold (a Word32 and two Word16s), so the mainnet follower refused every snapshot from block 5,581,257 on (`snapshotRefused`, `ConstraintViolation(Ptr, ... (16292793057, 1011302, 20) ... ptrStake)`): transaction 9a47e091 (block 5,567,164, slot 26,366,727, epoch 258, Mary) pays 50 ada to such an address. `Address.Mode` has a third case (`Backwards` below Babbage, `Rigorous` for Babbage, `Strict` from Conway, by `Mode.of(era)`); `Ptr.read` folds the groups into a `Word64`, normalises or refuses by the mode's `Ptr.Policy`, and every pointer address is kept as the normalised pointer written again, so the UTxO, the instant stake (`ptrStake` keys `Ptr 0 0 0`), the node-to-client answers, the Plutus context and the Haskell state codec agree with the reference; `TxOut.raw` stays as received and `TxOut.ledgerSize` counts the address the ledger holds. A refused snapshot is an Error (`snapshotRefused`) and the dashboard has a panel for it. No persisted format changes: the immutable and volatile databases are kept and the follower restarts from its snapshot at block 5,560,095 and replays ([findings.md](findings.md)). `MainnetPointerSuite`, `MainnetPointerStoreSuite`, `MainnetPointerSnapshotSuite`.

## D. Scale (P1)

- **D1** [#20](https://github.com/KD5UJC-XYZ/scarab/issues/20) (closed, not planned) More state on disk: accounts, pools, DReps and stake snapshots behind stores. Built and kept on branch `wip/d1-ledger-tables` (passed every gate, reached the Preview tip), but no heap saving at the tip (live set 329 MB with it, 272 MB without), and the Haskell node keeps this state in memory too (about 41 MB on Preview), so the node follows the reference ([ADR 0001](adr/0001-haskell-node-as-reference.md)). Reopen if mainnet memory (D6) shows this state dominating the heap; the snapshot read-back (#94) is the memory issue that matters.
- **D2** [#21](https://github.com/KD5UJC-XYZ/scarab/issues/21) (done; acceptance merged in PR #209) Parallel or optimised apply. Bounded dependency-batched Plutus workers after ordered preparation ([design](design/parallel-plutus.md)); pure serial reference retained. Current-rule continuous Preview replay passes 4,758,521 blocks, all 1,451 reference projections and the exact ordered 242 invalid transactions; all 68 failure windows agree in serial/four-worker modes. The captured epoch-135 window reduces summed validation time by 15.1%, with setup and scope in performance section 33.
- **D3** [#22](https://github.com/KD5UJC-XYZ/scarab/issues/22) (P1, done) ChainSync pipelining depth. The 256 timeout was not reproduced: 16 runs of 12 to 15 minutes against the public Preview relay at depths 64, 128, 200 and 256 (base build, this build, header-first on and off, and the pre-D8 scheduling on 2 CPUs) had no timeout; the upstream limits do not forbid 256 (reference client high mark 300, ChainSync ingress queue 462,000 bytes against 2 bytes per request, `shortWait` 10 s, the same as ours) and the relay answers a 256-header round in 0.26 s on average, 0.8 s at most. What was found and fixed: the receive path was quadratic (every byte read through a `Vector` of the whole buffer), 0.7 MB/s on 100 blocks of 90 KB, which on the connection shared with BlockFetch can hold ChainSync replies past the 10 s wait; 48 MB/s now. The default `--read-ahead` is **128** (64 is 6 to 10% slower, 128 to 256 are equal); the node logs the round times (`chainSyncRounds`) and slow single-block fetches (`slowFetch`). Details and numbers: [performance.md](performance.md) section 7. Remaining: the chain regions with large blocks (mainnet) were not reached; the reference client keeps up to 300 requests outstanding and collects down to 200, ours sends a round and collects all of it.
- **D4** [#23](https://github.com/KD5UJC-XYZ/scarab/issues/23) (done) Volatile blocks. The last k blocks are logged (`VolatileStore`) and applied again on start, and a graceful stop snapshots the immutable tip. Tested: restart equivalence with and without the log, a stop followed by a start that replays 0 blocks, copies of a running database at 12 points, the log torn at every record boundary; Preview restarts in [performance.md](performance.md). Remaining: no fault injection at the filesystem level (only truncated and flipped bytes), and a SIGKILL during the shutdown snapshot is the ordinary `kill -9` case.
- **D5** [#24](https://github.com/KD5UJC-XYZ/scarab/issues/24), extended by [#159](https://github.com/KD5UJC-XYZ/scarab/issues/159) (done) DB network identity: global format V6 binds protocol magic, Byron/Shelley genesis hashes and BLAKE2b-256 of the exact loaded Alonzo/Conway genesis bytes. A first-block predecessor is not historical proof for Shelley-start networks.

- **D7** [#26](https://github.com/KD5UJC-XYZ/scarab/issues/26) (done) Ed25519 throughput: the strict canonical-y check under [#147](https://github.com/KD5UJC-XYZ/scarab/issues/147) reduced mean verification time by 8.7% (134.0 to 122.3 microseconds; [performance.md](performance.md) section 19).
