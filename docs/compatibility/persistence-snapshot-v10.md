# Persistence: ledger snapshot format (V10) and the reference build

Part of the [compatibility matrix](../compatibility.md); the register entry is `persistence-snapshot-v10` in [compatibility.json](../data/compatibility.json).

## Status as recorded

implemented: native V10 (`SCRBSNPA`, #826) is the V9 layout ([V9](persistence-snapshot-v9.md)) with the reference build whose layout its Haskell state bytes are in recorded after the magic: a length byte and the `--reference-build` name, before the binding, outside the fingerprinted binding and sidecar schemas. The build is read before anything else because it decides the codec of the state bytes. `--reference-build` (on `follow`, `import-ledger-snapshot` and `export-ledger-snapshot`, `11.1` without it) names the build of `cardano-node` the network runs: `11.1`, the stable 11.1 release line behaving as its pinned release 11.1.3, or `leios-b004fe0c`, the unstable public Leios testnet build, whose layout import and export read and write ([its page](persistence-leios-state-layout.md)) and which `follow` refuses at start until its rules are implemented; `11.2`, the 11.2 release line pinned at 11.2.1, is named but refused at start by all three commands until its layout is implemented (`ReferenceBuildNotYet.Layout`), so no snapshot is recorded under it. The registered V9 → V10 step records `11.1`, keeps the binding and the Haskell bytes byte for byte and rewrites the sidecar in the V10 schema, which since the owner's in-place change of 2026-11-14 (#988, before any deployment) holds the follow state where V9's holds the bootstrap state, the flag and the lite ledger dropped and the era and epoch verdicts kept: every V9 writer encodes with the 11.1 codec or keeps bytes that codec decoded completely, and that codec refuses a Dijkstra state (`DijkstraNotYet.LedgerState`) and the Leios build's three-part `ExtLedgerState`, as the reference's 11.1 decoder does (ouroboros-consensus 82ecba32 `Ledger/Extended.hs:268-280`). Import keeps the input `state` bytes and records the build that wrote them; input that does not decode completely in that build's layout is refused. Export writes the recorded bytes unchanged and names their build; a requested build of another layout is refused. Nothing is converted between builds. The restore's fallback mirrors the reference's `tryNewestFirst` case by case: too-recent and undecodable snapshots, those of another build and those whose checkpoint keys do not decode among them, are deleted with their checkpoints, the snapshot file and each checkpoint best effort; those of another checkpoint layout or sidecar schema are kept; what the reference raises (an unreadable file, an absent checkpoint, an unknown Scarab format version) stops the start and deletes nothing. The migration of previous files takes the same fallback, and the V9 to V10 step copies the binding and the Haskell bytes as they were.

## Evidence

`fixtures/snapshot-v10` holds the registered conversions of the 17 `fixtures/snapshot-v9` files, each the V9 file with the five bytes of the `11.1` record after the magic and its sidecar converted (regenerated deterministically at #988); `SnapshotGoldenSuite` re-derives every one byte for byte, checks the binding and Haskell bytes against the source and the sidecar against the source's converted, and migrates the V5, V7, V8 and V9 goldens once, all ending at the same V10 bytes. `CodecSuite` pins the header bytes of every build; the binding fingerprint is that of V9, and the sidecar fingerprint that of V9 until the in-place change of #988. `SnapshotV10MigrationSuite`: committed V9 files migrate once to the maintained V10 files and read as them; the 11.1 codec refuses a three-part `ExtLedgerState` and trailing bytes; a V10 file recorded under `leios-b004fe0c`, under `11.2` or under an unknown name is refused before its state bytes are read; a restore skips such a file, with an error naming both builds, and takes an older snapshot or none. `LedgerSnapshotImportSuite` and `LedgerSnapshotExportSuite`: the recorded and reported build, the refused undecodable input, the refused export of another build's snapshot, and the export of a V9 file not yet migrated; `SclsBaseSuite` exports the same SCLS artifact from a V9 base not yet migrated, read in memory. `ReferenceBuildStartSuite`: `follow --reference-build leios-b004fe0c` and `follow --reference-build 11.2` exit 1, and `export-ledger-snapshot --reference-build 11.2` exits 2, before the database is touched; `LedgerSnapshotImportBuildSuite`: the import refuses `11.2` before its other inputs. `ReferenceBuildSuite`: the names, the pins against `docs/data/reference-pins.json`, both layouts' codecs, the refusal of the Leios build's rules at start and the warning without `ExperimentalHardForksEnabled`.

## Explicitly unchecked or unconfirmed

The Leios build's rules are selected by the build for one rule so far (#832) and not otherwise yet (#826 step c), nor its Dijkstra state read (step d). A snapshot recorded under another build is treated as the reference treats one it cannot decode: skipped with a warning naming both builds, deleted with its checkpoint (every native snapshot is temporary in the reference's sense) and the next older one tried (ouroboros-consensus 82ecba32 `Storage/LedgerDB/API.hs:599-646`; `SnapshotFallbackSuite` tests each case). Importing a Leios snapshot and then starting `follow` with the default `11.1` selection reaches this fallback outside tests. Preprod/mainnet writer upgrades remain #129 and #37/#115.
