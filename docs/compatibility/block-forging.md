# Block forging

Part of the [compatibility matrix](../compatibility.md); the register entry is `block-forging` in [compatibility.json](../data/compatibility.json). The three sections below are the cells of the former matrix row, unchanged.

## Status as recorded

implemented: Praos (Conway) only; G7-F3 retains typed terminal storage/unavailable/internal/defect outcomes, prevents signing after key-update failure and preserves the KES failure event/metric; ECVRF draft-03 proving, Sum6 KES generate/sign/evolve, opcert loading; typed operational-certificate input/verifier causes retained through OCERT, credential checks and reload refusals (#82); KES signing-key validation returns closed error cases with depth/period/length payloads, preserved through `ForgeError.KesKey` and `KesEvolution` (#82); dynamic block forging as cardano-node 11.1.3 (`Run.hs` 620-668, #906): a SIGHUP that finds the VRF key, the certificate or the KES key file absent disables forging (no slot started, no block, no KES write-back, `blockForgingUpdate` `DisabledBlockForging`, `forging_enabled_int` 0), a later SIGHUP that finds good files enables it, and `--start-as-non-producing-node`, `--non-producing-node` and `StartAsNonProducingNode` start with forging disabled; a reload forges with the VRF key it read, and from the opening of the stores a SIGHUP is the reference's initial one (topology read again, `blockForgingUpdate` `NotEffective`) and then the full one on every node (#919)

## Evidence

IETF draft-03 vectors 16 and 17 reproduced exactly; KES verification key reproduced from `cardano-cli` key seed; `Sum6KesSigningSuite`, `KeyFilesSuite`, `KesRotationSuite` (exact error cases and payloads, caller bytes retained, operator refusal leaves the key unchanged, terminal failure prevents later signing); `ForgerFailureSuite` (real rule/store failures, deferred defects, missing-file classification, cancellation and queued signers); `KesRotationSuite` dynamic forging (each of the three files absent disables forging with no slot, block or write-back; files back enable it after the reload checks; a refusal while disabled keeps it disabled; start as non-producing; the start-up trace; the key lock while disabled; the reference's reading order and `doesFileExist` rule), `MainArgsSuite` and `ConfigSuite` (the flags, the key and their precedence); `ForgeSuite`; `SystemStartSuite` and the geometry properties (slot clock), `ForgeSuite` counters; devnet `kes-rotate` (key rotated four times while forging, H2a); devnet `dynamic-forging` (#906: files moved away and SIGHUP, no block and no slot started in the 13 leader slots scheduled while disabled, no key written back, forging again after the files were put back; and #919: a SIGHUP during start-up answered `NotEffective` with the node running on; and #918: `kes-rotate` and `dynamic-forging` with the write-back by atomic exchange; [evidence log](evidence-log-5.md)); devnet `pool` (Scala node as pool 1 of three: 86 forged, 85 adopted, Haskell blocks-made 85 against 83.2 expected, 151 transactions, 18 KES periods, 16/16 comparisons)

## Explicitly unchecked or unconfirmed

Relative KES targets are checked before narrowing, with an exact typed cause and a terminal
outcome when a configured window outlasts the signing key. The source correspondence and
implementation are described in the [error design](../design/domain-errors.md); regression
coverage includes period 64, signed-Int overflow and 32-bit wraparound, same-key and replacement
reloads, configured-window expiry precedence, and period 63 as a usable control. These are
executed Scarab tests, not a native-node comparison on a pathological genesis. The separate
forging-window end-overflow discrepancy remains tracked in
[#474](https://github.com/KD5UJC-XYZ/scarab/issues/474#issuecomment-6759847567).

TPraos forging (H3); no Byron (PBFT) forging, a decision (H7); no KES agent (H2); the evolved KES key is written back to its file, which the Haskell node never does (H2a), and the KES key and certificate are reloaded on SIGHUP after a check the Haskell node does not make; the write-back never makes a key file that is not there; on Linux the evolved key replaces the file by `renameat2(RENAME_EXCHANGE)`, and elsewhere a move in the instant between the existence check and the rename can still put the key back ([#918](https://github.com/KD5UJC-XYZ/scarab/issues/918), ADR 0015 amendment of 2026-11-13); no bulk credentials file (#222); opcert issuing is the driver `scripts/pool/rotate_kes.py` (`cardano-cli` does the signing), exercised by the devnet `kes-rotate` only; on a public network, run on preprod only: from epoch 321 (2026-10-23) the producer forged in each of its first seven leader slots and six of those blocks are on the canonical chain, the seventh lost in a same-height battle (H1/H1a, [#115](https://github.com/KD5UJC-XYZ/scarab/issues/115), [evidence log](evidence-log-1.md)); mainnet not run; a slot the loop overran is not forged late, as in the reference, so at 1 CPU on a loaded host about one leader slot in a hundred runs was lost that way (evidence log; since #543 such a slot is passed over without a count, as the reference's `knownSlotWatcher` does); side-channel properties of the secret-scalar arithmetic not reviewed
