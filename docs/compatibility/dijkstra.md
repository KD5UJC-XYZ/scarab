# Dijkstra (next era)

Part of the [compatibility matrix](../compatibility.md); the register entry is `dijkstra` in [compatibility.json](../data/compatibility.json). The reference for Dijkstra is the build of the public Leios testnet (cardano-node `b004fe0c`, cardano-ledger `9df9f98c`, ouroboros-consensus `2416493b`; [decisions](../decisions.md), #711 and #54).

## Status as recorded

partial: the era is named; under `--reference-build leios-rc-2026w47` the node follows it and applies its blocks on the era rules, and the release builds refuse to enter it. Their maximum major protocol version is 11, and the Dijkstra trigger never fires below 12 (owner decision OD-4 on #54). Implemented as the Leios testnet build does it:
- the era, its place in the hard-fork sequence, and the typed `DijkstraNotYet` refusals (#801);
- block, header and transaction decoding (#806);
- the Dijkstra genesis and its protocol parameters (#807);
- the flat ledger rules BBODY, LEDGERS, LEDGER, UTXOW and UTXO (with Conway’s UTXOS), CERTS, CERT, POOL, GOVCERT and GOV, with failure types and reference tags, as entry points only tests reach (#54, T6); the node runs the era types' rules instead (below);
- UTXOW's check of the failing native scripts in Dijkstra's form, as `evalDijkstraNativeScript` evaluates them with the body's guards: a reference script with a guard, which the stored output keeps without a time-lock tree, is read again from the output's bytes and never passes unevaluated (#1126);
- the translation of a Conway ledger state into Dijkstra (#816);
- its transactions on the era types, of both levels, read from what the block decoder reads and equal to it on every Dijkstra transaction the repository holds, each pool registration with its parameters at the state's types and its voting key (`sppBlsKey`; #85);
- the certificate rules (CERTS, CERT, DELEG, POOL and GOVCERT), ENTITIES and the SUB rules on the era types, which the node runs within a Dijkstra block's BBODY under the Leios build (#85, #54). A withdrawal or direct deposit they apply changes an account's balance in `Word64` arithmetic that wraps, as the reference's `subtractCompactCoin` and `addCompactCoin` do (cardano-ledger 9df9f98c `libs/cardano-ledger-core/src/Cardano/Ledger/Coin.hs:202-218`, through `applyWithdrawals` and `applyDirectDeposits`, `State/Account.hs:284-305`). A withdrawal wraps a balance only on a transaction ENTITIES already refuses, for withdrawing past the account's original balance or, in the legacy mode, for not draining it (`Dijkstra/Rules/Entities.hs:291-296`). ENTITIES alone does not stop a deposit from wrapping a balance: a decoded deposit up to the `Word64` maximum into a registered account passes its checks, and the addition wraps as the reference's does. What bounds it is the ledger's value conservation, since a transaction cannot deposit more lovelace than it consumes and the supply is far below 2^64. So the wrap has no effect on consensus, persisted state or configuration; on the wire it is the value a later failure of the same refusal carries, as the reference's does (`DijkstraCertsSuite`). It is a Mirror;
- the upgrade of stored outputs with native reference scripts after a validated crossing block, preserving outputs created in Dijkstra (#815);
- the other parts of the crossing (#823): the mempool's transaction translation and rematch, the ledger-view forecast across the boundary, and the Praos to Praos2 chain-dependent state;
- the header gate's rules for a Dijkstra header under `--reference-build leios-rc-2026w47` (#54): Dijkstra's own ledger-view forecast or the one across the boundary, the chain-dependent state translated into Praos2's, and Praos2's envelope and protocol rules, as the build's ChainSync client runs them; the release builds keep refusing a Dijkstra header as of the wrong era;
- Dijkstra blocks applied by the node under the Leios build (#54), in the order of `Forker.applyBlock` (ouroboros-consensus `2416493b` `Storage/LedgerDB/Forker.hs:624-687`): a certifying ranking block's Leios checks against its parent's unticked state, a refusal being the block's; only once they hold, the certified endorser block's closure read from the endorser-block store and applied to that state before the tick, a missing or undecodable closure stopping the node as the reference's `error` does; then the tick, BBODY on the era types (the declared body size among its checks), and Praos2's header rules, checkpoints included, with the ledger view of the state ticked before BBODY (`applyHelper`, `Ledger/Extended.hs:297-311`), and the cumulative transaction bytes. A limit of this build that valid peer input can meet (a script the evaluator cannot judge, proposals the state's record cannot hold, the node's two readings of a block's bytes that disagree) withholds the block with no verdict: no peer is blamed and nothing is recorded invalid. Block application and the replays of the received log and the immutable store all run these rules; a failure of the node's own while the received log is replayed stops the start, and the chain it selected is not cut back. `follow` refuses the Leios build without an endorser-block store to open (`LeiosDbConfig.Backend: InMemory`, or neither `--db` nor `DatabasePath`), which a certifying block needs. The devnet chain from Origin, through the crossing, and the public testnet's first blocks are adopted as the reference adopted them (`MirrorDijkstraSuite`); the release builds keep refusing a Dijkstra block (`DijkstraNotYet.Rules`).

Under the Leios build the node's maximum major version is the configured one (12 on the testnet) and its era history enters Dijkstra, from the genesis on the public testnet, where the header gate validates the chain's headers (`DijkstraHeaderGateSuite`), and `follow` runs that build and applies its Dijkstra blocks. The release builds' maximum stays 11, which never enters Dijkstra.

The continuation is tracked in [#826](https://github.com/KD5UJC-XYZ/scarab/issues/826) for the
reference-build behavior, committee and state lifecycle, and Dijkstra persistence, and in
[#54](https://github.com/KD5UJC-XYZ/scarab/issues/54) for the remaining rules and production
integration. The experimental protocol-version work in
[#788](https://github.com/KD5UJC-XYZ/scarab/pull/788) follows an end-to-end crossing by Scarab;
the reference-only devnet evidence below does not satisfy that condition.

## Explicitly unchecked or unconfirmed

- **Not implemented:**
  - on the flat rules' test entry points only (the node runs the era types' rules, which have them): SUB rules and ENTITIES, LEDGER completing only for phase-2-invalid transactions without sub-transactions whose UTXOW checks are implemented (#54, T7);
  - guards, direct deposits, balance intervals, Plutus scripts, redeemers, datums and forms the Conway decoder refuses: they halt with `DijkstraNotYet.Rules` (#54);
  - the pool-registration transition and its VRF-key occurrence accounting (#826);
  - parameter-change proposals, whose store still holds Conway updates (#826);
  - A Dijkstra block's scripts run serially, a script the evaluator cannot judge is withheld without the transaction the other eras name, and its evaluations are not counted ([#85](https://github.com/KD5UJC-XYZ/scarab/issues/85#issuecomment-7067709618)); the epoch boundary is implemented: Dijkstra's EPOCH, SNAP (the Leios committee of `ppLeiosCommitteeSize`, the key age the KES constants give) and POOLREAP (one VRF-key reference released per pool, and the voting key of the future parameters adopted, keeping its registration epoch when the pool already holds it), checked byte for byte by `DijkstraEpochReferenceSuite` against the build's own TICK on both captured Dijkstra states across two boundaries, with and without the reward update, and on states derived from them with retirements and re-registrations (`fixtures/reference/dijkstra-epoch`), the states that hold future parameters with a voting key included (#826); the node's tick of a Dijkstra state runs that EPOCH on the era types, with the ratification and enactment the DRep pulser reaches, its governance state read from the stored record before each tick and written back after it, and the same cases give the build's states byte for byte through the node's tick, the cases with a proposed update of keys 47 and 48, which the stored record cannot hold yet, through the same tick on the era's record (#85);
  - the node-to-client queries and failure encoders;
  - a crossing forged by the Scala node on a devnet; the node follows one: on a Leios-build devnet (`devnet.py up-dijkstra`) it followed the chain from Conway into Dijkstra and across nine Dijkstra epoch boundaries, refusing and withholding no block (2026-11-21, #85).
- **Persistence:**
  - the Dijkstra ledger state in the 11.1 line's Haskell `state` layout (`DijkstraNotYet.LedgerState`); the Leios build's is read and written ([layout support](persistence-leios-state-layout.md)), its governance state as the era's record with its proposals' Dijkstra parameter updates (#826), but for a Peras epoch context (#826);

- **A Leios network:** state snapshots in every Shelley-based era, Dijkstra among them, can be imported and exported under the selected Leios build ([layout support](persistence-leios-state-layout.md)). A Dijkstra snapshot of a real database is imported once its point's block is: `import-haskell-db --reference-build leios-rc-2026w47` stores the chain's Dijkstra blocks, and the node applies them under that build (#54); [the offline replay](../leios.md#13-offline-replay-against-the-references-ledger-states-g1-54) replays the testnet's windows against the reference's states. Dijkstra's genesis injection is implemented at the ledger level (Conway's injection, the VRF key hashes counted and the Leios committee seated on the initial snapshots, `Dijkstra/Transition.hs:59-101`); under the Leios build the node starts a chain in Dijkstra when its configuration has `ExperimentalHardForksEnabled` and `TestDijkstraHardForkAtEpoch: 0`, as the public testnet's has (its maximum major protocol version is its own, 12, `Cardano/Node.hs:548-549`, ouroboros-consensus 2416493b), and `DijkstraGenesisStartSuite` checks that start, and its UTxO, against the build's own genesis state byte for byte. The major protocol version the node's forged headers carry is the build's own too (`cardanoProtocolVersion`, cardano-node b004fe0c `Protocol/Cardano.hs:192-194`): 12 with `ExperimentalHardForksEnabled` and 11 without, where the release builds keep 12 and 11; the minor is Scarab's CIP-0203 block producer identifier, 73 (255 with `--producer-id opt-out`), where the reference writes its release minor (12.0, 11.0, 11.2): an approved Deviation (#1348). A Dijkstra header holds the version as its version info (`extendHeaderBodyWithLeios`, ouroboros-consensus 2416493b `Shelley/Protocol/Praos.hs:275-300`). `ForgedProtocolVersionSuite` checks that under the testnet's configuration the node forges 12.73 (12.255 opted out), that the testnet headers after slot 2,168,639 the reference forged carry 12.0, its major, and that Dijkstra's BBODY accepts either signal against the testnet's parameters and refuses major 11 (`HeaderProtVerTooLow`). Under the Leios build the forger forges Dijkstra ranking blocks with Praos2 on a Dijkstra tip (#54): with the transactions of the pool's snapshot of the slot (`getSnapshotFor`, `DijkstraSnapshots.ofPool`), an endorser block for those past the ranking block's capacity, and certifying no endorser block; the pool admits Dijkstra transactions by Dijkstra's MEMPOOL under that build, with the reference's measures and capacity (#54); the block's ledger is the parent's state ticked once to its slot, as block application ticks it (#85). A release build's forger refuses a tip in Dijkstra (`ForgeProtocolProblem.Earlier`), and no build's forger carries a Conway tip's state into Dijkstra (`ForgeProtocolProblem.LeftConway`). Following that build applies its Dijkstra blocks (#54); the [selection scope](persistence-leios-state-layout.md#explicitly-unchecked-or-unconfirmed) distinguishes implemented rule selection from the remaining lifecycle work (#826). The endorser-block store exists, and `import-haskell-db` reads a Leios node's `leios.vol.db` and `leios.imm.db` into it; under the Leios build the node opens it, seeds chain selection's acquired endorser blocks from it, promotes the endorser blocks that immutable ranking blocks certify and collects it, and the fetch logic writes the endorser blocks and transactions it fetches into it (#54).
