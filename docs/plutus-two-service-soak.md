# Opt-in repeated JVM two-service soak supervisor

This is a disabled preparation checkpoint: both preflight and execution refuse until the repeated comparator has a completed, tested and reviewed integration. No live soak can launch through this draft. The unfinished comparison callsite only raises the same missing-capability error; it contains no ledger comparison and cannot return a success proof.

The intended `scripts/private_cluster_plutus_soak.py` is a separate, explicit research profile. It requires `--soak-profile early-restart-two-service-soak-v1 --epoch-mode repeated-jvm-v1`; after the missing integration is reviewed, the intended behavior without `--execute` is preflight only. The only requested durations are 120 seconds (smoke) and 600 seconds (target), with a 512-publication ceiling. Existing single-service, two-service and short fixture defaults are unchanged. The runtime retains an eight-block rollback window and compacts through checked owner anchor advancement; 512 is the total-publication ceiling, not a request to widen retained history.

The intended lifecycle first funds four independent script/collateral references on its disposable local reference network. Its separate spend fixture changes the tested transactions' upper validity bound to slot 8000; funding retains its existing slot-999 bound. One service exports an early epoch-zero checkpoint after one checked publication. The supervisor independently acquires that full point, validates the complete checkpoint/request pair and publishes a separate controller acceptance record. The old process must exit and be removed before the replacement is created. Recovery still passes through the reviewed Scala semantic replay path. The replacement has a fresh owner/checkpoint and an observed empty volatile admission pool. An independent second owner starts from the same original source. Both consume the same mutable reference chain.

The external HTTP client submits one original transaction to the independent owner, observes its inclusion, waits for both actual state pins to cross slot 1000 under changed environments, then submits the second original to the restored owner. It retains accepted/included responses and both body/witness originals in both publication streams. It never submits a tested spend with the reference CLI. Client completion does not end either service: each repeated runtime must report a complete active interval starting after peer readiness. The requested duration applies independently to the two final owners, whose start times differ; it does not establish that duration of simultaneous overlap or an independent peer surviving the restart. In this draft the checkpointing service stops before its replacement starts, and the separate peer starts after that replacement. Block-limit stops, early successful exits and shortened clocks are failures.

Each JVM generation retains the exact frozen request, JVM raw IEEE words and execution hashes under `jvm-likelihood/generation-NNNN`. The supervisor joins these hashes and FrozenID to checked publication/startup metadata. Completed recorder outputs from canceled, unpublished candidates are retained separately as unselected drafts and never count as publication evidence. Zero words are legitimate for empty pool domains. These records contain no native execution or parity claim. An independently run posthoc native comparison may consume the exact requests later; it cannot replace the recorded computation or retroactively become a runtime dependency.

Separate exact historical endpoint acquisitions and a dedicated repeated-state comparator are required after both services exit. The old same-epoch comparator cannot certify repeated snapshots, rewards or governance. Missing comparator support is a failure, not a partial pass. Acquisitions remain separate non-atomic observations. This profile does not claim full ledger validation, late-epoch restore, pending-transaction restoration or crash durability. The early restart does not itself establish that a user transaction preceded the checkpoint.

The reference container, two service slots and one serial helper remain within four CPUs/seven GiB; replacement reuses a vacated service slot. The outer operation is bounded to 720 seconds plus 30 seconds of cleanup. This is a hard cap, not a guarantee that setup, early restart, both complete active intervals and serial terminal oracles fit. The existing acquisition time-reserve checks remain in force and may refuse a run with insufficient time. Owned disk usage, file count, free space and evidence log sizes are monitored; Docker logs rotate at 16 MiB twice per owned container. Cleanup is bound to immutable owned container IDs, including the removed first process. Evidence and private keys stay outside Git.

The optional `NativeRuntimeMounts` extension belongs to the separate native-assisted restart path. It requires an independently supplied hash of the complete contained library set and exact read-only binary/library mounts. The JVM soak command accepts no such mounts or native executable flags.

Source-only tests and compilation do not establish live restart, multi-epoch parity or a successful 600-second run. Those require a retained successful execution and independent review of its five separate observations: join, early restart, two owners, post-boundary spend and full multi-epoch duration.
