# Opt-in repeated JVM two-service soak supervisor

This is a disabled preparation checkpoint: both preflight and execution refuse until the repeated comparator has a compiled, tested and independently reviewed integration. No live soak can launch through this draft. The supervisor has a separately unit-tested repeated comparison-result validator; satisfying that wire contract does not remove the unconditional launcher guard or establish native endpoint agreement.

The intended `scripts/private_cluster_plutus_soak.py` is a separate, explicit research profile. It requires `--soak-profile early-restart-two-service-soak-v1 --epoch-mode repeated-jvm-v1`; after the missing integration is reviewed, the intended behavior without `--execute` is preflight only. The only requested durations are 120 seconds (smoke) and 600 seconds (target), with a 512-publication ceiling. Existing single-service, two-service and short fixture defaults are unchanged. The runtime retains an eight-block rollback window and compacts through checked owner anchor advancement; 512 is the total-publication ceiling, not a request to widen retained history.

The intended lifecycle first funds four independent script/collateral references on its disposable local reference network. Its separate spend fixture changes the tested transactions' upper validity bound to slot 8000; funding retains its existing slot-999 bound. The independent peer starts first and must produce a checked publication and a successful HTTP state observation before a second service exports an early epoch-zero checkpoint after one checked publication. The supervisor independently acquires that full point, validates the complete checkpoint/request pair and publishes a separate controller acceptance record. The old process must exit and be removed before the replacement is created. Recovery still passes through the reviewed Scala semantic replay path. The replacement has a fresh owner/checkpoint and an observed empty volatile admission pool. The independent peer keeps the same running container, Docker PID/start timestamp (with zero restarts), and runtime owner throughout checkpointing and restore. The reference producer is not frozen or restarted during that stage: authority uses an exact historical-point acquisition while it continues producing. A second HTTP observation must show strict progress under the unchanged peer owner after checked rejoin. Both consume the same mutable reference chain.

The external HTTP client submits one original transaction to the independent owner, observes its inclusion, waits for both actual state pins to cross slot 1000 under changed environments, then submits the second original to the restored owner. It retains accepted/included responses and both body/witness originals in both publication streams. It never submits a tested spend with the reference CLI. Client completion does not end either service: each repeated runtime must report a complete active interval starting after peer readiness. The target is actual simultaneous following, not two independent service lifetimes. An explicit JVM-only soak profile gives the peer a lifetime of target + 120 seconds and the restored owner target + 60 seconds (720 and 660 at the 600-second target). The restored follower must start within 90 seconds of the peer. Final loop intervals, measured after peer intersection and before transport teardown, must overlap by at least the target after a conservative two-second endpoint uncertainty discount; each wall-clock interval must agree with its monotonic elapsed time within one second. The peer interval must contain both retained HTTP observations around restart. Missing intervals, insufficient overlap, changed owner/container or clock inconsistency reject the run. Block-limit stops, early successful exits and shortened clocks are failures.

Each JVM generation retains the exact frozen request, JVM raw IEEE words and execution hashes under `jvm-likelihood/generation-NNNN`. The supervisor joins these hashes and FrozenID to checked publication/startup metadata. Completed recorder outputs from canceled, unpublished candidates are retained separately as unselected drafts and never count as publication evidence. Zero words are legitimate for empty pool domains. These records contain no native execution or parity claim. An independently run posthoc native comparison may consume the exact requests later; it cannot replace the recorded computation or retroactively become a runtime dependency.

Separate exact historical endpoint acquisitions and a dedicated repeated-state comparator are required after both services exit. The old same-epoch comparator cannot certify repeated snapshots, rewards or governance. Missing comparator support is a failure, not a partial pass. Acquisitions remain separate non-atomic observations. This profile does not claim full ledger validation, late-epoch restore, pending-transaction restoration or crash durability. The early restart does not itself establish that a user transaction preceded the checkpoint.

The repeated runtime hook selects its pure typed export from the coherently frozen final owner snapshot. Its separate terminal schema has a 2 MiB observation ceiling; the existing 1 MiB output-map/result and 128 KiB publication ceilings remain unchanged. The supervisor binds the full terminal owner pin, original observation/output bytes, initial source and manifest, and each independent endpoint manifest/acquisition receipt. It requires all supported UTxO, stake, snapshots, epoch components, governance, reward, raw non-myopic and protocol comparisons to succeed. Actual fee pots are compared as epoch components: the same-epoch `feesAfter = feesBefore + 600000` shortcut is invalid across reward processing. Active reward pulsing must fail explicitly unless its complete cursor/snapshot semantics are supported; it cannot be relabeled complete.

The reference container, two service slots and one serial helper remain within four CPUs/seven GiB; replacement reuses a vacated service slot. The explicit operation cap is 1080 seconds plus 30 seconds of cleanup. The conservative stage plan reserves 120 seconds for setup, at most 750 seconds from peer start through restored lifetime (90 + 660), 15 seconds for terminal capture/finalization availability, and two serial endpoint stages of 57 seconds acquisition plus 35 seconds comparison: 1069 operation seconds at target 600. The result timestamp check bounds loop end to terminal capture within 15 seconds; it does not by itself measure outer generation-resource finalizers. Result-file availability and remaining-time checks bound the complete stage. Remaining-time checks precede stages; this is a bounded plan, not a promise of completion. Acquisition and restart occur while the peer remains alive. Existing unflagged and native-assisted runtime lifetime limits remain unchanged. Owned disk usage, file count, free space and evidence log sizes are monitored; Docker logs rotate at 16 MiB twice per owned container. Cleanup is bound to immutable owned container IDs, including the removed first process. Evidence and private keys stay outside Git.

The optional `NativeRuntimeMounts` extension belongs to the separate native-assisted restart path. It requires an independently supplied hash of the complete contained library set and exact read-only binary/library mounts. The JVM soak command accepts no such mounts or native executable flags.

Source-only tests and compilation do not establish live restart, multi-epoch parity or a successful 600-second run. Those require a retained successful execution and independent review of its five separate observations: join, early restart, two owners, post-boundary spend and full multi-epoch duration.
