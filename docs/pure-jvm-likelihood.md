# Bounded pure JVM likelihood generation

`ConwayLikelihoodGeneration.generateJvm` computes likelihood words from a genuine captured `ConwayEpochBoundary.Frozen` and its exact ID. The result retains that object; `forFrozen` rejects a different or reconstructed capture even with an equal ID. Publication still requires the coordinator's current-state fence. This component does not establish intervening chain freshness, authorize a ledger publication, or relax the existing nonempty-go generator guard.

The explicit `PureJvm` mode takes no native response, executable or attestation. It computes probability with JVM `Math.pow`, then the 100 midpoint likelihood samples with `Math.log` and the original Float cast ordering. Inputs remain restricted to 1,000 epoch slots, f=1/20, d=0, at most 64 supplied pools, positive circulation, pool stake between zero and circulation, and previous block counts 0..1000. Pool stake is divided by circulation, not normalized pool stake. Supplied zero-stake entries remain represented.

`Generated.evidence` retains canonical original bytes; `nativeResponse` is absent in PureJvm. Computed raw32/raw64 counts are separate from native comparison counts, which are zero. `nativeValidated`, `nativeValuesAuthoritative`, `diagnosticNativeDependency` and `generalJvmParityValidated` are false. Zero mismatch counters without comparisons do not establish parity. Existing `CheckedJvm` still requires exact raw native comparison and selects computed JVM words; `AssistedNative` remains separately explicit. The native acceptance factory and native resource both reject PureJvm rather than providing an implicit fallback.

`JvmLikelihoodGenerator.resource` records each serialized bounded invocation in a fresh evidence directory. It uses the historical shared Oracle interface but never allocates a native process or native resource. Each `generation-%04d` directory contains `request.txt`, `jvm-result.txt`, and `execution.txt`. Files use CREATE_NEW. The counter saturates at the configured maximum (1..128); released handles refuse new work. Release closes the handle and waits for owned in-flight work. Filesystem writes have cooperative cancellation/liveness, not a hard I/O deadline; partial evidence on failure is retained and never accepted as a completed generation. There are no detached writes.

The request retains the existing `conway-native-likelihood-v1` canonical format so an independent post-run verifier can execute the pinned native helper against precisely those bytes. JVM output starts `conway-jvm-likelihood-result-v1`, repeats the entire request, then `--jvm--` and ordered rows containing pool ID, 16 hexadecimal probability bits, and 100 concatenated eight-hex Float words. The six-line execution receipt is: `jvm-likelihood-execution-v1`, request SHA256, JVM output SHA256, `PureJvm`, computed raw32/raw64 counts, and `0 0` native comparison counts.

An external post-run verifier must bind the request Frozen ID and output hash to the actual published generation, execute the pinned native helper, verify its complete request echo/domain, and compare every raw probability and Float word exactly. Directory numbering alone is not epoch authority. A mismatch must remain visible; there is no tolerance pass or replacement of JVM transition values with native output. Native source/binary/library pins belong to that separate differential execution, not to the pure JVM runtime receipt.

Finite native golden tests establish exact agreement for their supplied cases only. They do not prove universal JVM/native floating-point parity or full repeated-epoch ledger correctness. Runtime mode selection and supported governance/reward composition are separate reviewed components.
