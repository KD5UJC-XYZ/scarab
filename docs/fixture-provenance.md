# Cardano fixture provenance

## What these fixtures prove

`fixtures/cardano-golden.tsv` contains six rows: the original serialized transaction
body and original full transaction envelope for each of three Conway translation
golden cases. Its columns are `name`, `kind`, `cbor_hex`, `expected_hash`, separated
by tabs, with a comment-prefixed header. Kinds are `transaction-body` and
`transaction-envelope`; both expect the same 32-byte transaction ID.

The expected hashes are **read from committed Haskell-generated TxInfo outputs**,
not generated by the Scala lab or by the Python verification hash. The extraction
also checked every selected body against Python's Blake2b-256 implementation as an
independent packaging sanity check. A separate [offline Haskell CLI check](offline-reference-checks.md)
has decoded the three unmodified full transactions and matched all three IDs.
We did not run Haskell ledger validation, a node, or chain replay. These tests exercise byte preservation, envelope slicing,
and transaction hashing; they do not establish semantic transaction validity,
ledger conformance, consensus interoperability, or Plutus evaluation conformance.

The corpus is synthetic golden data, not a claim that these transactions appeared
on mainnet. The Plutus language labels below describe the expected TxInfo version;
all three transactions are serialized Conway-era transactions at protocol major 10.

## Exact extraction and expectations

The top-level corpus is an indefinite-length array. Each zero-based case is a
five-field array `(ProtVer, SupportedLanguage, UTxO, Tx, VersionedTxInfo)`.
`Tx` is case field 3, and its first array element is the body. Raw slices were
copied without decoding/re-encoding. `VersionedTxInfo` is `[constructor, record]`;
the record starts with a constructor number. V1's zero-based TxInfo field 9 and
V2/V3's field 11 contain TxId, therefore record array indices 10 and 12,
respectively. The TxId newtype is `[0, bytes]`. Those bytes supply `expected_hash`.

| Case index | TxInfo language | Body bytes | Envelope bytes | Expected transaction ID |
| --- | --- | ---: | ---: | --- |
| 44 | PlutusV1 | 3,790 | 16,022 | `ffa3e217dec2cec2f5d4f9ec60dce862332454c65dd1cab08d796ca8f2951355` |
| 57 | PlutusV2 | 4,956 | 13,813 | `c2b1815ec5ffbcafb810a857dc18a035884949ac34fc14d04df545f469d6cd17` |
| 42 | PlutusV3 | 8,567 | 13,658 | `d39e160bd2cc34dbdf270f5a956fb1f663385eb9c5e900534c4ed937b331e080` |

All selected bodies contain indefinite-length containers (2, 1, and 5 respectively),
and the full envelopes contain 89, 107, and 46. These are structurally nontrivial
vectors, chosen to cover three TxInfo versions without vendoring the entire corpus.
The transaction ID hashes the **original body bytes only** with Blake2b-256.
It does not hash the full envelope or a normalized re-encoding of the body.

`fixtures/raw/*.cbor` contains the six exact binary slices. The JSON file
`fixtures/extraction-manifest.json` records, for each slice, its SHA256 and
zero-based, half-open byte range in the decompressed original corpus. It also
records the original byte range and full newtype encoding of each expected TxId,
allowing the source of the expectation to be verified independently of hashing.
The TSV is an alternate hexadecimal encoding of those slices, not additional
independent test vectors. `fixtures/SHA256SUMS` checks the packaged files.

To audit extraction, download the pinned corpus, verify its SHA256, then for each
manifest artifact compare `corpus[start:end]` to that raw file. Compare the expected
TxId encoding at its separately recorded range. Finally compare the raw file's
hex encoding to the corresponding TSV field. This does not require trusting the
lab's CBOR parser or hash implementation.

## Reproduce and verify without Scala

From the repository root, explicitly download the original uncompressed corpus,
then run the independent, standard-library-only Python extractor in verification
mode (the default). The script itself never makes network requests:

```sh
curl --fail --location \
  https://raw.githubusercontent.com/IntersectMBO/cardano-ledger/226b002d5b5e83e24355f8a28ab214f3259eabda/eras/conway/impl/golden/translations.cbor \
  --output /tmp/cardano-ledger-translations.cbor
python3 fixtures/extract_verify.py /tmp/cardano-ledger-translations.cbor
(cd fixtures && sha256sum -c SHA256SUMS)
```

The extractor checks the pinned corpus SHA256 before parsing, independently
rediscovers the three cases and source spans, reads the expected IDs from the
Haskell TxInfo fields, and reconstructs all six raw slices, the complete TSV, and
the manifest in memory. It demands byte-for-byte equality with every packaged
derived file. It separately checks Blake2b-256 against the recorded expected IDs.
It preserves the distinction between definite length 31 and indefinite containers
and handles tags and indefinite arrays, maps, and chunked byte/text strings.

To regenerate into a separate empty directory for comparison:

```sh
python3 fixtures/extract_verify.py /tmp/cardano-ledger-translations.cbor \
  --write --output /tmp/cardano-fixture-rebuild
diff fixtures/cardano-golden.tsv /tmp/cardano-fixture-rebuild/cardano-golden.tsv
diff fixtures/extraction-manifest.json /tmp/cardano-fixture-rebuild/extraction-manifest.json
diff -r fixtures/raw /tmp/cardano-fixture-rebuild/raw
```

`--write` generates only the six raw files, TSV, and extraction manifest; it does
not download or rewrite licenses, notices, documentation, or checksums. The full
5.7 MB corpus is deliberately not redistributed in this narrow lab.

Version 0.4.0 adds two raw Haskell-generated Conway integration-test sequences (four transaction events) distributed by pinned Blueprint and Amaru commits, plus the original protocol-parameter evidence. This is a separate corpus from the codec/TxInfo translations above. See [predicate scope and source anchors](ledger-conservation.md) and `fixtures/ledger/provenance.json` for lossless projection and source/member provenance. Success means only the selected predicate is satisfied; archived ledger booleans and source assertions supply expectations. No ledger oracle was executed here.
