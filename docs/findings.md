# Findings against real data

Facts about the Cardano ledger and consensus that the specifications do not make obvious and that
this project learned from comparing against the Haskell node and the public Preview chain, each with
where it was found and what pins it now. They are observations to confirm against the reference
source, not authoritative statements. Roadmap IDs (B1, ...) point into [roadmap.md](roadmap.md).

## The six Preview ledger bugs

Syncing the whole Preview chain was the first check of the ledger against a public network and
found six bugs that the devnet could not show. The first two were located by comparing reserves,
treasury, reward pot and single-pool stake with Koios per epoch; the others from the failing
transaction recorded with `follow --plutus-cases`.

| Where | What the node did | What the ledger does | Commit | Pinned by |

## Decoders under hostile input (K3)

Found by the `fuzz` project ([running.md](running.md#fuzzing-the-decoders-roadmap-k3)): mutated fixtures and
CDDL-sampled items against 53 decoder entry points, about 6.4 million cases in the longest run (4 seeds of
30,000 per target), 20,000 per target in every `check`. The decoders were already bounded by design (item,
string and depth limits, lengths checked before allocation, typed errors); the fuzzer found two kinds of gap
and nothing else. Each fix is the minimal one; the regression tests hold the minimised inputs.

| Finding | Where found | Pinned by |
|---|---|---|
| **Nesting within the depth limit overflows the stack.** `Cbor.Limits.maxDepth` is 2048 (raised from 64 for a Preview datum), but a recursive function over the decoded tree needs more stack than a thread has for the deeper part of that range: `Cbor.encode` threw `StackOverflowError` for 927 bytes of `81 81 ... 00` (about 900 nested arrays) and `PlutusData.decode` for about 400 nested maps (`a1 00 a1 00 ...`) on the fuzz thread. `Cbor.decode`, `Cbor.encode` and `PlutusData.decode` now catch the overflow and return the error `Cbor.TooDeep` (`Cbor.stackSafe`). **Open:** the depth that a thread survives depends on its stack size, so the verdict on a very deep, otherwise valid datum depends on the thread that decodes it; the Haskell node has no such limit below its own. An iterative decoder, or decoding on a thread with a stack sized for 2048 levels, would make it deterministic. Every Plutus data consumer goes through `PlutusData.decode` (redeemers, datums and inline datums in `ScriptContexts`), so the guard covers them; what is not guarded and not fuzzed is the recursion that follows decoding (`ScalusEvaluator.toData`, the machine, the equality and hashing of `PlutusData`; the evaluator already catches `StackOverflowError` around the evaluation itself), and the phase-2 translation as a whole is not a fuzz target. | fuzz `cbor` and `plutus-data` (seed 1), minimised by the shrinker | `CborSuite` (regression K3), `DecoderRobustnessSuite` (256 KiB stack thread) |
| **Pointer address: a long run of continuation bytes costs quadratic time and memory.** `Ptr.decode` accumulated each 7-bit group with `(acc << 7) + d` on a `BigInt`: a pointer address of 5.5 KB allocated 27 MB, and an address as long as a block body (up to 90 KB; the CBOR string limit allows 1 MB) several hundred MB to GB per decode, from one transaction output. The groups are now packed into a byte array and converted once (linear; 100,000 continuation bytes decode in milliseconds); the decoded value is unchanged. **Open, a difference from the reference** (cardano-ledger `Cardano.Ledger.Address` at `f649f975`, read for this finding): the ledger decodes a pointer's slot as a Word32 and its transaction and certificate indexes as Word16 (`decodePtr`) and, from decoder version 9 (Conway), refuses an address with a larger value; before that (`decodePtrLenient`, versions below 9) it reads Word64 with wrap-around and normalises a value beyond the fields to the dangling pointer (0, 0, 0). We keep the exact value in every era, so a Conway transaction with such an address is accepted here and refused by the reference. Not fixed: it needs the era-dependent rule and the dangling-pointer semantics of the stake distribution, i.e. a ledger change. | fuzz `address-and-output` (allocation bound), minimised by the shrinker; ledger source | `DecoderRobustnessSuite` (100,000 continuation bytes in under a second; the value at every length from 1 to 70 groups) |
| The decoders did not allocate for declared-but-absent lengths: a 10-byte input declaring 2^60 (or 2^32, 2^31) array elements, map pairs or string bytes fails within 4 MB of allocation in every one of the 53 targets, alone, nested, behind tags and inside indefinite items; every head of the seed items rewritten that way likewise. No code change. | `GuardSuite` | `GuardSuite` |
| A refusal `VersionMismatch` carries the versions the peer listed that we do not know (`unknown`); they are parsed and kept in the message, but `Handshake.encode` writes only the known list, so a refusal is not re-encoded to its input. Harmless (we never send a refusal on behalf of a peer); the round-trip property ignores the field. | fuzz `handshake-ntn` | `fuzz` property |
| **What the fuzzer cannot do.** It finds exceptions, hangs and blow-ups, not wrong verdicts: between 1 and 25 percent of the inputs of a target decode, so rules behind a valid transaction (the ledger rules, script evaluation) are reached only through valid seeds. The 6.4 million cases in the longest run are many for the decoders and few for the ledger. Storage files and the JSON configuration are not fuzzed. | design | [compatibility.md](compatibility.md) |

## Method

The recurring pattern: compare per-epoch aggregates (reserves, treasury, rewards, pool stake) with
an independent source (Koios on Preview, LocalStateQuery on the devnet) to find the epoch, then
record the failing transaction (`--plutus-cases`) or capture the blocks (`CaptureMain --from`) into a
fixture and fix against it.
