# Findings against real data

Facts about the Cardano ledger and consensus that the specifications do not make obvious and that
this project learned from comparing against the Haskell node and the public Preview chain, each with
where it was found and what pins it now. They are observations to confirm against the reference
source, not authoritative statements. Roadmap IDs (B1, ...) point into [roadmap.md](roadmap.md).

## Decoders under hostile input (K3)

Found by the `fuzz` project ([running.md](running.md#fuzzing-the-decoders-roadmap-k3)): mutated fixtures and
CDDL-sampled items against 53 decoder entry points, about 6.4 million cases in the longest run (4 seeds of
30,000 per target), 20,000 per target in every `check`. The decoders were already bounded by design (item,
string and depth limits, lengths checked before allocation, typed errors); the fuzzer found two kinds of gap
and nothing else. Each fix is the minimal one; the regression tests hold the minimised inputs.

| Finding | Where found | Pinned by |
|---|---|---|
| **Nesting within the depth limit overflows the stack.** `Cbor.Limits.maxDepth` is 2048 (raised from 64 for a Preview datum), but a recursive function over the decoded tree needs more stack than a thread has for the deeper part of that range: `Cbor.encode` threw `StackOverflowError` for 927 bytes of `81 81 ... 00` (about 900 nested arrays) and `PlutusData.decode` for about 400 nested maps (`a1 00 a1 00 ...`) on the fuzz thread. `Cbor.decode`, `Cbor.encode` and `PlutusData.decode` now catch the overflow and return the error `Cbor.TooDeep` (`Cbor.stackSafe`). **Resolved by B17** (the first version of this note left it open): the depth that a thread survived depended on its stack size, and the reference has no limit below the size of the block; decoding, encoding and the walks over the decoded item now keep their stack on the heap (see the ledger finding "No nesting limit below the size of the block"), so the verdict no longer depends on the thread. `Cbor.stackSafe` stays as a last resort for recursion that remains (`==`/`hashCode`/`toString`). ## Method

The recurring pattern: compare per-epoch aggregates (reserves, treasury, rewards, pool stake) with
an independent source (Koios on Preview, LocalStateQuery on the devnet) to find the epoch, then
record the failing transaction (`--plutus-cases`) or capture the blocks (`CaptureMain --from`) into a
fixture and fix against it.
