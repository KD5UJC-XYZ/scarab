# Incremental injection numeric coefficients

Part of the [performance log](../performance.md).

## 42. Incremental injection numeric coefficients (#499)

On 2026-10-26, the unchanged four-seed fuzz run at `798daf559` completed locally in 2,342
seconds, including 1,786 seconds in the incremental injection reader. The CI job reached its
60-minute limit without completing this target or printing a counterexample. Its result is
incomplete: the retained output cannot distinguish aggregate cost from shrinking after a
per-input time-guard failure. No cases, seeds, mutation distribution, resource guards or workflow
limits were changed to address it.

A local thread sample identifies `BigInteger.destructiveMulAdd` under the reader's coefficient
conversion during ordinary property evaluation. The original native corpus includes a 262,145-digit
coefficient. Inspection of the installed ScalaCheck 1.19 bytecode confirmed that successful-case
Pretty wrappers are lazy; the sampled cost was parsing, not eager formatting of successful test
arguments.

The reader constructs large coefficients by splitting their decimal digits at the midpoint,
parsing leaves of at most 163,840 digits with the existing BigInt constructor, and combining
`left * 10^rightWidth + right`. The width includes leading zeros. Typed explicit frames and a
tail-recursive loop keep outside-data width stack safe; the power cache is immutable and local
to one conversion. Smaller inputs keep direct construction. No mutable or global cache is added.
The original `Json.fromBigInt`, BigDecimal and checked Scientific fallback constructors remain
unchanged, including their convenience-accessor behavior.

This changes only the exact Integer construction algorithm. Native json-stream 0.4.6.1
`Data/JsonStream/CLexer.hs:129–172` constructs an arbitrary Integer coefficient and then Scientific
with a separate exponent; scientific 0.3.8.1 stores that pair without normalization. Grammar,
signs, fraction width, wrapped exponent, chunk-sensitive acceptance and native partial-number
limits remain unchanged. The algorithm does not impose a new digit limit.

Measurements used the same Docker JDK 21.0.11 image, a two-CPU quota,
`-XX:ActiveProcessorCount=2`, `-Xss8m` and a 12-GiB container memory limit. Each row measures the
unchanged target's complete parse and existing resource checks, after earlier cases had initialized
the JVM. These are individual observations under comparable host load, not a throughput claim or
an average across repeated fuzz runs. Allocation is total allocated bytes, not live heap; MB is
decimal.

The improvement trades allocation for CPU time. Two independent fresh test forks measured the
cold 327,679-digit root at 349,816,240 allocated bytes against the unchanged 352,845,824-byte bound:
only 3,029,584 bytes (0.86%) of margin. That narrow margin is reported rather than described as
broad headroom. Cold timings were 791 and 807 ms; the unchanged per-input time limit is two
seconds. This focused result does not establish that the full CI fuzz job now completes.

Smaller balanced leaves were rejected because the actual native seed exceeded the existing
allocation guard, despite faster arithmetic in isolation. Uneven 2:1 and 3:1 splits increased
allocation and time in the bounded arithmetic comparison. A checked canonical integer-string
constructor reduced allocation but did not materially improve end-to-end CPU cost. A zero-scale
BigDecimal representation was rejected because its returned MathContext differed from the original
constructor. None of those alternatives changes the selected product path.

The target uses 65,536-byte feeds. Its largest terminating coefficient is 327,679 digits at the
beginning of the input or 327,674 after the object-key prefix; signs and other number syntax consume
space within that bound. Another all-number chunk still encounters the reference's existing
partial-number refusal. This is distinct from the largest generated byte input: the largest corpus
seed is 327,686 bytes, and four existing duplication mutations reach 5,242,976 bytes. Other mutation
steps cannot exceed that bound because their additions are at most the largest seed or 200,000
bytes. The maximum byte-input control exercises the unchanged refusal/resource boundary, not
conversion of a five-million-digit coefficient. Larger single-chunk API inputs remain covered by
exact-value and stack-safety tests.

`InjectionJsonSuite` retains all 73 native traces and their complete coefficient/exponent events.
`InjectionDecimalSuite` checks full returned coefficient text and Integer equality, decimal-width
boundaries, signs, zeros, wrapped exponents and small-stack traversal. Its 15 constructor/accessor
controls compare full text, equality, hashing, exact BigDecimal unscaled value, scale and MathContext,
`toBigInt`, and `toLong`. Circe's convenience `toBigInt` accessor has a 262,144-digit bound even on
values constructed from BigInt; complete coefficient observations therefore use returned integer
text uniformly, without dropping larger cases.

`InjectionDecimalGuardSuite` runs the original target's unchanged guards over every native seed,
width boundaries, cold maximum coefficients and the maximum generated byte size. Additional
repeated-coefficient semantic tests verify that every array element is constructed; they do not
claim arbitrary aggregate resource conformance. The original parser itself exceeded the two-second
limit on a separate four-coefficient aggregate stress input. Focused results do not replace the
mandatory complete four-seed fuzz run or CI.
