# Next slice: public Praos VRF certificate checks

Research date: 2026-10-08 UTC. Cloud-only isolated research; no main repository edits. No signing, proving, key generation, private fixture tables, live nodes, sockets, peers, Docker, dev-host, authentication or publication. No `unsafeRunSync`.

## Result and recommendation

A bounded next slice now has **two genuine archived preprod header positives**, beyond the three generic IETF positives underpinning version 0.7. Recommend a pure `PraosVrfCertificate` layer that constructs the exact protocol alpha and verifies the claimed output using the existing experimental draft03 primitive. Keep this explicitly experimental and avoid calling its result “valid header”.

The two headers, slots **70070331 and 70070379**, come from the public Amaru corpus pinned at `34a453005bcaaf837ee73bd996b99eab8ef92961`. With the public nonce from that revision’s test state, both pass the existing pinned native draft03 verifier and produce exactly the 64-byte claimed output in the header. These are archived public preprod artifacts, not outputs generated by our Scala implementation, and no prover was used. The repository labels them preprod; this pass did not independently authenticate their historical inclusion on that chain.

## Pins and source-derived contract

The existing `vrf-wrapper-sources/provenance.json` records and hashes these exact release pins:

- Consensus: `82ecba329d7d054340bf707d44fe6e9ac27cec40`.
- Ledger: `f649f9751074d2ab3de033fc3912f29c9862c1f5`.
- Cardano-base: `060819b59c184b951a54e3c563304983c53a3eac`.
- Sodium: `dbb48cce5429cb6585c9034f002568964f1ce567`.

[Ledger Praos VRF](https://github.com/IntersectMBO/cardano-ledger/blob/f649f9751074d2ab3de033fc3912f29c9862c1f5/libs/cardano-protocol/src/Cardano/Protocol/Praos/VRF.hs) defines `mkInputVRF` and raw signable bytes:

1. Slot is unsigned Word64, domain 0 through 18446744073709551615, encoded as exactly eight big-endian bytes.
2. An ordinary epoch nonce contributes its raw 32 bytes. `NeutralNonce` contributes **no bytes**. It is not an all-zero 32-byte nonce.
3. Alpha is Blake2b-256 of that concatenation: 8-byte preimage for neutral, 40 bytes for ordinary. Alpha is always 32 bytes. No CBOR, textual hex, era discriminator, network magic or length prefix enters this hash.
4. The supplied nonce is protocol state, not a header field and not recoverable from one isolated header.

[Cardano-base `verifyCertified`](https://github.com/IntersectMBO/cardano-base/blob/060819b59c184b951a54e3c563304983c53a3eac/cardano-crypto-class/src/Cardano/Crypto/VRF/Class.hs#L359-L369) verifies the proof for the key and alpha, then compares the resulting output to `certifiedOutput`. The certificate’s separate output is not decorative. [Consensus `doValidateVRFSignature`](https://github.com/IntersectMBO/ouroboros-consensus/blob/82ecba329d7d054340bf707d44fe6e9ac27cec40/ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos.hs#L570-L599) additionally checks pool registration/key hash and leadership threshold; those are outside this proposed slice.

Suggested pure API (proposal, not implemented):

- `EpochNonce = Neutral | Hash32(owned Bytes)`.
- `PraosVrfInput(slot: UInt64, nonce: EpochNonce)`; expose a checked constructor from BigInt if Scala has no dedicated UInt64 value. A signed Long must not silently reject the upper unsigned half or encode a negative semantic slot.
- `alpha(input): Either[InputError, Bytes32]`.
- `verify(input, key32, proof80, claimedOutput64): CertificateResult` using `StrictDraft03.verify` once.
- Results distinguish malformed protocol input/envelope, cryptographic proof rejection, claimed-output mismatch, verified certificate output, and internal failure. Preserve existing owned immutable bytes; a mismatch never yields a “verified claimed output”.
- Accept explicit Praos input, not a generic era enum that silently treats TPraos the same. Leave header CBOR extraction in a separate boundary. A future decoder must preserve original header bytes for other hashes/signatures.

## Praos versus TPraos

At the pinned Cardano composition, Shelley/Allegra/Mary/Alonzo use TPraos; Babbage/Conway and the source’s future Dijkstra composition use Praos. Source presence of Dijkstra does not establish activation on any network. Do not select the VRF profile from a current wall-clock date or an advertised protocol version without the hard-fork context.

[TPraos `mkSeed`](https://github.com/IntersectMBO/cardano-ledger/blob/f649f9751074d2ab3de033fc3912f29c9862c1f5/libs/cardano-protocol/src/Cardano/Protocol/TPraos/BlockHeader.hs#L404-L431) starts with the same slot/nonce Blake2b-256 digest, then XORs a universal-constant nonce. `seedEta = mkNonceFromNumber 0`; `seedL = mkNonceFromNumber 1`. The latter helper hashes a Word64 big-endian number with Blake2b-256. [TPraos overlay](https://github.com/IntersectMBO/cardano-ledger/blob/f649f9751074d2ab3de033fc3912f29c9862c1f5/libs/cardano-protocol-tpraos/src/Cardano/Protocol/TPraos/Rules/Overlay.hs#L160-L184) checks two separate certificates (nonce and leader), unlike unified Praos.

Praos output usages are also distinct from alpha/certificate validity: leader range extension hashes ASCII `L` plus the output; nonce use hashes ASCII `N` plus output, then hashes again to form a nonce. These belong in later explicit modules. A valid certificate alone does not establish leader eligibility or correct nonce evolution.

The hash-gated library is the previously authorized offline self-build, SHA-256 `76b41125c867878a1b0cfe64dde580872f61ca4cc6fae06223e902e3e803b24f`. This pass called only `crypto_vrf_ietfdraft03_verify`, after 32/80-byte key/proof checks. ## Tests executed and proposed admission gates

Executed `python3 cardano-research/praos-header-probe/check_public_headers.py`:

- Four archived headers examined, two accepted certificate matches and two context-unestablished rejections.
- Sixteen native mutation rows based only on the two accepted headers: original, wrong slot, little-endian slot, neutral nonce, zero nonce, proof bit flip, key bit flip, claimed-output bit flip.
- Exactly two composite certificate successes. Native proof verification succeeds in four rows: the two originals and their wrong-claim versions. The latter must fail the certificate layer despite valid primitive proofs.
- Fifteen independent source-derived alpha controls: slots 0, 1, 2^63−1, 2^63 and 2^64−1, crossed with neutral, zero and ascending-byte nonces. `alpha-controls.json` records preimages and Python Blake2b-256 digests. These are **source-derived controls, not reference-Haskell golden outputs**.

Before implementing/admitting a next slice, retain immutable evidence hashes and exact provenance; add portable source-independent corpus admission similar to 0.7; test native-oracle expectations against Scala without generating expected values from Scala; exercise nonces of 31/33 bytes, claims of 63/65 bytes, nulls, negative/overflow slot input, immutable ownership, unexpected/fatal failure categories, concurrency and no unchecked output path. Keep local resource policy separate from consensus rules. Explicitly reject or leave unsupported TPraos/header-era inputs, rather than returning an accidental success on a superficially similar payload.

## Disqualified or deferred fixture routes

The pinned consensus Babbage/Conway serialization goldens were downloaded and source-traced. [Shelley Examples](https://github.com/IntersectMBO/ouroboros-consensus/blob/82ecba329d7d054340bf707d44fe6e9ac27cec40/ouroboros-consensus-cardano/src/unstable-shelley-testlib/Test/Consensus/Shelley/Examples.hs#L238-L256) translates a TPraos body and coerces its nonce certificate to the unified Praos field. They are useful codec goldens, **not established valid Praos cryptographic fixtures**. No false-positive corpus claim is made from their “golden” name.

The documented `gen-header` route is not safe unchanged for this scope: [pinned source](https://github.com/IntersectMBO/ouroboros-consensus/blob/82ecba329d7d054340bf707d44fe6e9ac27cec40/ouroboros-consensus-protocol/src/unstable-protocol-testlib/Test/Ouroboros/Consensus/Protocol/Praos/Header.hs) generates keys/proofs/signatures and its JSON context serializes signing keys. It also renders `NeutralNonce` as 32 zero bytes while parsing valid hex as ordinary nonce, so blindly treating that format as a neutral-nonce golden would be wrong. No generator was run and no JSON secret context was downloaded. Amaru’s separate 107-row header-test-cases JSON likewise has generator-context secret fields according to its reader; it was not downloaded. Retained source files are implementation text, not those private fixture tables.

## Scope still unsupported

This establishes a promising narrow future conformance slice, not implementation approval or full consensus correctness. Still outside scope: pool registration/VRF-key hash binding, stake snapshots and threshold arithmetic, KES/opcert verification and counters, epoch nonce derivation/evolution, hard-fork and era-history validation, header/block size and body hashes, chain selection, rollback, network validation, full CBOR admission, mainnet historical authenticity and universal cryptographic equivalence. Accepted mixed-order proofs and independent cryptographic review from 0.7 remain open. The Amaru snapshot is a separately pinned public archive, not the Cardano 11.1.3 implementation oracle; acceptance evidence comes from the pinned draft03 verifier plus exact-release alpha/claim semantics.

Amaru public source/fixtures retain the Apache-2.0 notice (`amaru-LICENSE`); consensus/ledger licensing and existing sodium fixture notices remain separately applicable. A future integration should retain source URLs, artifact hashes and notices rather than embedding these as unexplained bytes.
