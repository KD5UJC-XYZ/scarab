# Conway to Dijkstra devnet chain (reference only)

Status: Current — original native chain input for the Dijkstra codec and rule work (#54).

A capture of the `devnet.py up-dijkstra` reference cluster: a 3-pool network of the build the public
Leios testnet runs, which starts in Conway and forks into Dijkstra at epoch 1, with one Dijkstra
transaction. Scarab took no part in the run: it cannot follow a Dijkstra chain yet, so this is
reference output only. Read with [docs/leios.md](../../docs/leios.md) (section 12, the Leios reference)
and [the Leios fixtures](../leios/README.md).

Recorded on 2026-11-04 (the manifest's `capturedAt`) with

```sh
python3 scripts/devnet.py --name dijkstra-t11a up-dijkstra       # returns once the transaction's block is immutable
python3 scripts/devnet.py --name dijkstra-t11a capture-dijkstra  # writes this directory from node 1's ImmutableDB
python3 scripts/devnet.py --name dijkstra-t11a down
```

## Cluster parameters

Network magic 1082026, k = 5, f = 0.2, epochs of 200 slots of 0.1 s. Every Shelley-based era up to
Conway starts at epoch 0, Dijkstra at epoch 1 (`TestDijkstraHardForkAtEpoch`), with
`ExperimentalHardForksEnabled`, so headers carry protocol version 12.0. The Shelley genesis has
protocol 12.0 as the testnet's does, and the ledger reports major 12 in both epochs; no governance
action was submitted.

The network comes from `cardano-cli dijkstra genesis create-testnet-data`, with the testnet's
Alonzo, Conway and Dijkstra genesis files of the image as specifications and its Shelley
genesis with the funds, delegates and stake removed and the parameters above. The node
configuration is the image's, with this network's genesis hashes, without `MinNodeVersion`, and
with tracing to stdout only.

| Era | Blocks | First block | Notes |
|---|---|---|---|
| Conway | 0-32 | block 0, slot 4 | tag 7, 5-element blocks, empty |
| Dijkstra | 33-40 | block 33, slot 202 | tag 8, `[header, [txs, leios_cert, peras_cert]]`; block 37 (slot 225) holds the transaction |

The manifest's `eras` are tips `up-dijkstra` saw while polling, so its first Dijkstra entry can be
a later block than the first Dijkstra block above; `firstDijkstraBlock` is taken from the capture.

## Files

| File | Contents |
|---|---|
| `blocks.tsv` | 41 blocks, contiguous from Origin to the third block after the transaction's, read from node 1's ImmutableDB chunk files. Columns: block tag, block number, slot, header hash (Blake2b-256 of the header's original bytes), the `[tag, block]` in hex. The whole chain is kept because the epoch nonce folds in every VRF output. |
| `headers.tsv` | The original header bytes of the last three Conway blocks and every Dijkstra block, as above with the header in the last column. Each header is also in its block. |
| `transaction.json` | The transaction as `cardano-cli dijkstra transaction sign` wrote it: a text envelope of type `Tx DijkstraEra` whose CBOR is the 3-element mempool form. In block 37 the same transaction is the 4-element block form, `is_valid` last (cardano-ledger `9df9f98c` `eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Tx.hs:152-182`). Its id is in `manifest.json`. |
| `manifest.json` | Image, binary versions, blocks per era, the first Dijkstra block, the transaction's id, block and slot, the plan, the protocol major per epoch, the cluster parameters and the SHA-256 of `blocks.tsv`. |
| `genesis/*.json` | The exact genesis files and node configuration the nodes read. `shelley-genesis.json` must stay byte-identical: the initial Praos nonce is its Blake2b-256 hash. |

`scripts/tests/test_devnet_dijkstra.py` checks that the files are what the capture code writes
from the blocks, that the chain is contiguous, and the transaction's place and forms.

## Cross-check with the pinned ledger

Every block was decoded by the Leios testnet block oracle (`scarab-leios-testnet:local`, cardano-ledger
`9df9f98c`, [its README](../../scripts/oracle/leios-testnet/README.md)), each as a case of kind `block`:
all 41 accepted, with the same tag and header hash as `blocks.tsv`, and for the Dijkstra blocks the
same block number and slot and version `[12, 0]`. In block 37 the oracle reports the one transaction
with the id in the manifest, valid. The oracle's output is not kept here.
