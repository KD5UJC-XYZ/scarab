Plutus reference data from IntersectMBO/plutus (Apache-2.0): one copy, with every pinned release
read as a view of it. `releases.json` records each release's tag, commit, the sha256 of its codeload
archive, and the file count and digest of its view.

The top-level directories hold the base release (`base` in `releases.json`) whole. An older release
keeps only the files that differ from the base, under `overlays/<tag>/` in the same layout, and lists
the base files it lacks as `absent`. Tests read a view through `PlutusReference` (Scala) or
`release_view` in `scripts/plutus_reference.py`, never a path of their own.

What a view holds, unmodified unless noted:

- `conformance/`: `plutus-conformance/test-cases/uplc/evaluation`, the `.uplc` programs,
  `.uplc.expected` results and `.budget.expected` budgets. The `.flat` encodings, their
  `.flat.expected` results, and the READMEs and helper scripts of that tree are left out.
- `cost-model/`: `plutus-core/cost-model/data/builtinCostModel{A..E}.json` and
  `cekMachineCosts{A..E}.json`, the default builtin costing functions and machine step costs of each
  builtin semantics variant.
- `ledger-api/V{1,2,3}-param-names.txt`: derived. The constructors of `data ParamName` in
  `plutus-ledger-api/src/PlutusLedgerApi/V{1,2,3}/ParamName.hs`, in declaration order (the order of
  the on-chain cost model parameter list), one per line.

The six malformed `conformance/builtin/parser/value` cases also have Scarab-generated
`.flat.cbor.hex` sidecars, listed as `generated` in `releases.json` and shared by every release (the
programs they encode must be the same in each). They preserve the entries of the upstream `.uplc`
literals in their written order, including repeated keys, empty token lists and zero quantities. They
are CBOR byte strings containing the original Flat program, generated by
`PlutusBoundaryCorpus.malformedValues` with `FlatProgram`. The text parser otherwise normalises those
malformed maps before the Flat decoder sees them.

`python3 scripts/plutus_reference.py check` (offline, in CI) confirms each view against its recorded
digest. `verify` downloads each pinned archive and compares the views with it file by file, and
`add-release <tag> <commit>` makes a newer release the base and moves the older ones to overlays.
